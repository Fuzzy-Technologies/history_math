# Article PDF editions

Every rendered article has a localized PDF download near its title. Jekyll renders the original Markdown, figures, footnotes and literal dollar formulas once; the existing local KaTeX renderer typesets the same formulas for the screen and PDF. The exporter extracts explicit print regions from this same rendered HTML, excluding navigation, related articles and build timestamps. Playwright Chromium prints these regions with a dedicated A4 stylesheet. No second editable text, PDF binary or image derivative is committed.

Run `bundle exec jekyll build --trace` followed by `npm run build:pdf`, then run output and browser checks. For a custom destination, run `node scripts/article-pdf.mjs --site-dir <destination>`. The manifest generated by Jekyll supplies the base path, actual article URLs, language and PDF paths; root-domain builds work too. CI and production run this stage before checking local URLs. Published PDFs travel only with the required Pages deployment artifact; CI still uploads only its small text reports.

PDF manifest version 2 binds every file to `/assets/pdf/<language>/<article-slug>-<language>.pdf`, with exactly one terminal `-ru` or `-en` suffix. Already localized archive slugs retain their existing suffix; examples without a localized HTML route receive it only in the PDF name. The native download attribute declares that same basename, so the two editions keep distinct filenames outside the website. Language/route mismatches, old unsuffixed names and version-1 manifests are rejected. The owner-approved migration retires unsuffixed PDF URLs without duplicating heavy files as aliases.

The filename migration changes the exporter fingerprint and invalidates prior PDF cache entries. Its master publication rebuilds all admitted PDFs automatically and clears the old output filenames. Later publications resume normal incremental reuse. Print layout, images, type, formulas and pagination rules remain unchanged.

PDFs use compact horizontal Russian/English journal mastheads, embedded PT Serif and KaTeX fonts, the site's light-theme paper (`#f4eddf`), chocolate ink (`#33271f`), copper accents, page numbers, repeated table headers and bounded illustrations. The same light palette supplies secondary text, captions, citation lines and footer text, regardless of the reader's screen theme. Native Chromium margin boxes extend the solid paper color to every edge and corner of every sheet while retaining the existing A4 content margins. Article text remains selectable; links point to the public website, never the temporary local rendering server. Print-only image downsampling targets roughly 240 dpi at the rendered size. Source image files and screen rendering remain unchanged. The decorative paper grain is omitted to avoid multi-megabyte per-page raster backgrounds.

Full master publications run `python3 scripts/check_pdf_colors.py <site-directory>` on the actual project-path and configured Pages PDFs. Poppler rasterizes each page at a bounded resolution; the check scans all four margin bands and corners for white strips and requires the correct body/title ink in each document. Illustration-only pages are allowed. The source suite checks print/light palette consistency and rejected page colors without generating PDFs. This gate stays outside the light article-only publication path.

The print planner may shrink figures within its twenty-percent limit or move them past up to two preceding paragraphs. Its unfragmented height estimates do not impose page breaks: if neither adjustment fits, the figure returns to its original position and Chromium places the figure and caption together using `break-inside: avoid`. This prevents estimated overflow from leaving a mostly empty page when the actual print layout has room.

The manifest only includes documents admitted by the existing publication gate. Ordinary builds cannot export draft PDFs. Explicit review builds retain the review notice. The exporter clears its public PDF output before every run and repopulates it only from the current manifest, preventing a removed or unpublished article from surviving as an orphaned file. Cached bytes never determine publication eligibility. Missing pages, failed assets, unrendered formulas, clipped tables/formulas, invalid language/path bindings or a wrong logo fail the export and publication pipeline.

Checks cover RU and EN export, project/root paths, invalid manifest inputs, stale-output removal, PDF signatures and the downloadable link. Visual review uses rendered PDF pages; read-only extraction checks text, page count and link annotations. Native English translation notices are pages, so they do not acquire a misleading English article PDF.

## Incremental generation

The ignored `.pdf-cache` directory stores content-addressed PDFs outside all site output. Each key includes the rendered print document, public origin and base path, original article images, transitive stylesheet/font/image dependencies, local KaTeX scripts, exporter implementation, dependency lockfile, actual Chromium executable and Linux fallback font bytes. Shared dependencies are hashed once per invocation. A change to an article or one of its images invalidates that article; print styles, fonts or the renderer invalidate all affected articles. Menu text, home-page content, related-article navigation and build timestamps do not invalidate PDFs. The shared main stylesheet is conservatively included, so any change to it also invalidates PDFs.

Every cache hit checks the PDF signature and SHA-256 against its metadata. Missing/corrupt/incomplete entries are regenerated. Missing source assets still fail a warm build. Cache writes use temporary files and atomic renames; superseded entries are pruned for the current origin/base-path namespace after a successful export. Different origins and base paths never reuse a PDF with the wrong public links. Linux uses Fontconfig to fingerprint fallback fonts; other platforms render each time instead of assuming their system fonts are unchanged.

The default is two concurrent pages in one browser. Use `--jobs 1` through `--jobs 4` (or `PDF_JOBS`) to bound CPU/memory use, `--cache-dir <directory>` (or `PDF_CACHE_DIR`) for an alternate external cache, and `--force` for a full rebuild. A fully cached run never launches Chromium. Each run prints a summary with rendered/reused/total counts and elapsed seconds. The PDF subprocess has a 45-minute cold-build budget; CI jobs have 60 minutes. Other article-check subprocesses retain their existing three-minute limit.

CI and deployment restore an Actions cache before PDF work. Only successful master verification/deployment jobs save it; PRs and the opt-in review job only restore. Both jobs use the same prefix and validate individual entries regardless of the archive-level hit. No extra PDF artifact archive is uploaded. Cache eviction or a first build requires a full render; caching improves repeat builds, not the fundamental cost of printing a new collection. Cache upload/download and Jekyll/browser checks still take time. An unavailable cache remains a performance miss, not a publication dependency.

`node tests/pdf-cache-browser.mjs` (after `bundle exec ruby tests/publication_test.rb`) exercises real RU/EN rendering, warm reuse, isolated text/image changes, shared-style invalidation, forced rebuilds, corruption, missing assets and withdrawn-article cleanup. Unit checks cover transitive dependencies, marker failures and cache integrity; the existing PDF fixture/browser checks retain formula, link and language coverage.

For an optional real-render load measurement, run `node tests/pdf-scale.mjs 1000` after the publication fixture test. It creates isolated copies of the reading demo, measures cold/warm builds and a single edit, and asserts render counts. This is a synthetic workload, not a guarantee for a thousand long illustrated articles. It is excluded from routine CI.
